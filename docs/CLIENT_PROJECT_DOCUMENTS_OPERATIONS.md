# OMNIFACTORY Client Workspace — документы, согласования, уведомления

Этот релиз зависит от **PR #54** (`feat/client-project-lifecycle-20261119`).
Не объединять его непосредственно в основную ветку до слияния PR #54.

## Что работает

- Оператор платформы публикует ограниченный по длине **текстовый документ** для конкретного заказа: техническое задание, описание результата или другой документ.
- Каждая публикация создаёт **новую неизменяемую версию**, а не переписывает прежнюю. Уникальность обеспечивается на уровне БД.
- Владелец клиентской организации может подтвердить **только актуальную версию**. Подтверждение фиксирует actor_id и время в БД; повторный запрос идемпотентен.
- При публикации следующей редакции старое подтверждение сохраняется в истории, но не подтверждает новую версию.
- Оператор не может передать проект на приёмку, если последняя опубликованная редакция технического задания ещё не согласована. Приёмка клиентом выполняет ту же проверку.
- Новый заказ, публикация документа, изменение статуса, назначение исполнителя и приёмка создают **персональные** уведомления активным пользователям организации. Прочитанность хранится для каждого адресата отдельно.
- Данные доступны через `/account/projects/{id}`, `/support/projects/{id}`, `/account/notifications`. Доступ проверяется на сервере по клиентской организации или операторскому allowlist, на всех POST используется CSRF.

## Чего здесь нет

- Приёма/хранения бинарных файлов и вложений (PDF, DOCX, изображения).
- Юридически значимой электронной подписи, КЭП или договора-оферты.
- Email/SMS/Telegram push-уведомлений.
- Автоматического подтверждения стоимости или запуска оплаты.

Ручной сценарий: оператор публикует спецификацию v1 → клиент согласует → оператор публикует v2 → старое согласование нельзя повторно применить к v2 → статус review недоступен до одобрения v2 → клиент видит новое уведомление → отмечает его прочитанным → оператор передаёт на приёмку → владелец организации подтверждает результат.
